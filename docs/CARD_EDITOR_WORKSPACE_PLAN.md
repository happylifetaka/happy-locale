# CardEditingWorkspace分割・状態と操作の所有整理計画

作成日: 2026-09-16
状態: 計画作成済み・実装未着手

## 目的

[前回の追加改善計画](./CARD_EDITOR_REFACTORING_PHASE2_PLAN.md)で、`CardEditor.vue`は1,516行になった。
処理のcomposable化は進んだが、状態の生成、機能間の調整、Canvas・Inspector等への接続が親に集中している。
状態と操作の所有場所を整理し、カード編集画面を`CardEditingWorkspace.vue`として分離する。

成功の基準は、行数だけでなく次の点とする。

- 領域編集の変更を追う際に、プロジェクト保存やアセット管理まで読む必要が減る。
- Workspaceが操作を処理でき、親への単純なイベント中継が減る。
- 状態の生成・更新・リセット・解放の担当が明確になる。
- Undo/Redo、保存、画面切り替え、IME、非同期処理の現在の動作を維持する。

前回は、現在の所有構造のまま大きなUIラッパーを追加すると中継が増えるため採用しなかった。
今回は、共有する状態と操作の境界を先に整理することで、この制約を解消できるか検証する。

## 設計方針

### 「所有」の意味

所有者は、値を置く場所だけでなく、生成、変更ルール、リセット、終了時の後始末を担当する。
参照するコンポーネントが増えても、同じ状態を複数箇所で生成したり、watchで双方向同期したりしない。

| 対象 | 所有・更新の方針 |
| --- | --- |
| 保存する文書・カード一覧・共有設定 | 既存の`useProjectStore`を維持 |
| 編集中のカードとカード別Undo/Redo | `useCardEditor`の同一インスタンスを共有し、変更は既存操作を通す |
| ブラシ等の共有ツール状態 | 既存の`useEditorToolsStore`を利用。追加は複数の利用者と寿命が説明できる項目に限定 |
| カード画面内の表示状態・領域選択とUIの連携 | Workspaceと専用composableへの移動候補。画面外の利用者を調べて決定 |
| 保存・読込・プロジェクト切り替え・画面切り替え | `CardEditor`側の全体調整に残す |
| 画像・フォント・Object URL・フォルダハンドル | `useProjectRuntime`を維持し、解放担当を一つにする |
| OCR・翻訳等の実行状態 | 既存の機能別composableを維持。共有Workerや一括処理はエディター全体の寿命で管理 |
| ダイアログの未確定入力 | ダイアログ内で管理し、確定操作から反映 |

### 共有方法の使い分け

- 親子間で完結する値・操作はprops、v-model、イベントを使う。
- 複数部品が使うツール設定はPiniaを使う。
- エディター内で共有する既存の編集状態・操作は、型付き`provide/inject`を第一候補とする。
- 提供するAPIは「領域編集」「カード画面への外部操作」等の利用目的で絞り、親の全変数を一つの巨大オブジェクトにしない。
- 共有APIを作る場合、必要な参照と操作関数を渡す。資源の所有権やストア全体を不用意に渡さない。
- 子ごとに`useCardEditor()`を呼ばない。現在の実装では呼び出すたびに独立した状態と履歴ができる。
- Piniaへ履歴や全機能を移すことは今回の前提にしない。

候補の構成:

```text
CardEditor（全体の初期化・保存・画面切り替え・終了）
├─ 編集状態と操作を共有する窓口（既存インスタンスを提供）
├─ CardEditingWorkspace（カード編集UIとその連携）
│  ├─ CardCanvas
│  └─ Inspectorと領域編集関連UI
├─ CardList（配置・所属は工程0で判断）
├─ AssetEditor
└─ PrintLayoutWorkspace
```

共有窓口は新しい状態の複製ではない。名前・ファイル構成・提供範囲は依存調査後に確定する。
CardListには一括OCR、翻訳、書き出し、カード追加等の全体操作があるため、Canvasと同時に移すことを必須にしない。

## 共通の進め方

1. 現在の利用者、更新経路、寿命を確認する。
2. 現行動作を固定する回帰テストを先に追加し、変更前に通す。
3. 一つの所有境界・更新経路ずつ変更する。
4. 対象テストで確認し、工程の区切りで全体検証する。
5. 効果と残った依存を記録し、適切な粒度でコミットする。

これは既存動作を先にテストで固定してから構造を変える、TDDに近い進め方とする。
テスト失敗時は原因を確認し、期待値の緩和やskipで通さない。
不具合が見つかったら分割を止め、再現テストと修正を別コミットにまとめ、成功後に分割を再開する。
既に合意した範囲の不具合修正は都度の承認待ちにしない。仕様が不明な点は確認する。

## 工程0: 所有・依存・寿命の棚卸し

- [ ] 作業ツリー、現行コード、既存テストの基準結果を確認する。
- [ ] Canvas、Inspector、CardList、関連ダイアログについて、参照値・操作・外部利用者を一覧化する。
- [ ] 領域選択、タブ、表示倍率、previewMode、描画遅延、保護領域選択の所有者を決める。
- [ ] ToolbarのUndo/Redo、画像書き出し用Canvas API、一括OCRから候補への反映等、画面外との接点を明記する。
- [ ] カード・プロジェクト・画面の切り替え、エディター終了時の保持／リセット／解放を表にする。
- [ ] 同時に複数のエディターを表示する利用経路の有無を確認し、既存Pinia状態の共有範囲も記録する。
- [ ] Workspaceの初期範囲と、CardList・OCR・フォントUI・各ダイアログの所属を決定する。

受け入れ条件: 各状態と資源の所有者が一つに決まり、UIを移しても寿命が変わらない設計を説明できる。

## 工程1: 分割を守る回帰テスト

既存テストを再利用し、不足する振る舞いだけを追加する。

- [ ] 領域選択がCanvasとInspectorに反映され、タブ遷移と選択解除が維持される。
- [ ] Inspectorの変更、Canvasの移動・描画、ToolbarのUndo/Redoが同じ編集履歴を使う。
- [ ] カード切り替えで履歴や選択状態が混ざらない。
- [ ] カード→アセット／印刷→カードの往復で、倍率・表示状態・編集結果が現行規則どおりに保たれる。
- [ ] 入力中の描画遅延と確定後の反映が維持される。
- [ ] 確認ダイアログの取消と古い対象への適用防止を維持する。
- [ ] OCR・画像読込中の画面切り替えとエディター終了で、現行の継続／中止／資源解放が維持される。
- [ ] 再マウント後に前回の状態や非同期結果が混入しない。

受け入れ条件: 現行実装で対象テストが通る。重要な接続は実コンポーネントの連携またはPlaywrightで検証し、親のスタブだけに依存しない。

## 工程2: 状態と操作の共有境界を整える

**実際の責務の移動はここから開始する。Vueコンポーネントの切り出しは工程3で行う。**

- [ ] 最初は領域選択・領域変更・履歴への接続を対象とし、型付きの小さな共有APIを定義する。
- [ ] 編集状態は一度だけ生成し、同じインスタンスを利用できるようにする。
- [ ] 更新を既存の`useCardEditor`／`useRegionEditing`経由に保ち、保存ストアへの直接更新を増やさない。
- [ ] 選択とタブ遷移等の連携を担当する場所を整理し、親の取次処理を削除する。
- [ ] 既存のツールストアと重複する状態を作らず、リセット担当を維持する。
- [ ] 共有APIの追加によって、参照箇所や中継が本当に減ったか確認する。

受け入れ条件: 領域編集の経路が明確で、Toolbarを含む既存操作が同じ履歴を使い、状態の二重生成がない。

## 工程3: CardEditingWorkspaceを切り出す

- [ ] 工程0で決めたCanvas・Inspector中心のUIを`app/components/CardEditingWorkspace.vue`へ移す。
- [ ] 画面内で完結する接続と表示状態を一緒に移す。外部参照のある状態は共有境界を利用する。
- [ ] 親へのprops・イベントに単純な中継を追加せず、Workspaceで操作を処理する。
- [ ] Canvas APIの書き出し・背景色取得を既存利用者へ接続し、参照の登録・解除と未準備時の扱いを確認する。
- [ ] 現在の`v-show`による保持を維持し、画面の往復で編集状態を作り直さない。
- [ ] DOM構造、CSS、レイアウト、タブのキーボード操作、ダイアログ表示を確認する。
- [ ] Workspace単体の連携テストを追加し、親側にも保存・画面切り替え等の境界テストを残す。

受け入れ条件: カード編集UIの変更をWorkspace側で追え、親が個々の領域編集を取り次がず、ブラウザ上の動作が維持される。

## 工程4: 残った接続を評価して整理する

- [ ] 移動する機能は対象テストを先に確認し、一つずつ変更する。

- [ ] 親の全propsを一つのオブジェクトに包んだだけの箇所や、不要になった中継・watchを除去する。

受け入れ条件: 追加の分割に効果がない項目は理由を記録して残し、行数目標のための分割をしない。

## 設計の根拠

共有状態のストア管理、provide/injectによる中継の削減、状態と更新操作をまとめる考え方はVue・Piniaの公式に沿う。
Workspaceの範囲や具体的な共有APIは、このアプリの依存と寿命に合わせて決める設計判断である。
