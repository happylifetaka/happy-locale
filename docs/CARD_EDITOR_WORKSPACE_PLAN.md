# CardEditingWorkspace分割・状態と操作の所有整理計画

作成日: 2026-09-16
状態: 実装中（状態の所有整理、型付き共有API、Workspace UI分離を実装・検証済み）

## 目的

[前回の追加改善計画](./CARD_EDITOR_REFACTORING_PHASE2_PLAN.md)で、`CardEditor.vue`は1,516行になった。
処理のcomposable化は進んだが、状態の生成、機能間の調整、Canvas・Inspector等への接続が親に集中している。
状態と操作の所有場所を整理し、カード編集画面を`CardEditingWorkspace.vue`として分離する。

成功の基準は、行数だけでなく次の点とする。

- 領域編集の変更を追う際に、プロジェクト保存やアセット管理まで読む必要が減る。
- Workspaceが操作を処理でき、親への単純なイベント中継が減る。
- 状態の生成・更新・リセット・解放の担当が明確になる。
- Undo/Redo、保存、画面切り替え、IME、非同期処理の現在の動作を維持する。

前回は、現在の所有構造のまま大きなUIラッパーを追加すると中継が増えるため採用しなかった。
今回は、共有する状態と操作の境界を先に整理することで、この制約を解消できるか検証する。

## 設計方針

### 「所有」の意味

所有者は、値を置く場所だけでなく、生成、変更ルール、リセット、終了時の後始末を担当する。
参照するコンポーネントが増えても、同じ状態を複数箇所で生成したり、watchで双方向同期したりしない。

| 対象 | 所有・更新の方針 |
| --- | --- |
| 保存する文書・カード一覧・共有設定 | 既存の`useProjectStore`を維持 |
| 編集中のカードとカード別Undo/Redo | `useCardEditor`の同一インスタンスを共有し、変更は既存操作を通す |
| ブラシ等の共有ツール状態 | 既存の`useEditorToolsStore`を利用。追加は複数の利用者と寿命が説明できる項目に限定 |
| カード画面内の表示状態・領域選択とUIの連携 | Workspaceと専用composableへの移動候補。画面外の利用者を調べて決定 |
| 保存・読込・プロジェクト切り替え・画面切り替え | `CardEditor`側の全体調整に残す |
| 画像・フォント・Object URL・フォルダハンドル | `useProjectRuntime`を維持し、解放担当を一つにする |
| OCR・翻訳等の実行状態 | 既存の機能別composableを維持。共有Workerや一括処理はエディター全体の寿命で管理 |
| ダイアログの未確定入力 | ダイアログ内で管理し、確定操作から反映 |

### 共有方法の使い分け

- 親子間で完結する値・操作はprops、v-model、イベントを使う。
- 複数部品が使うツール設定はPiniaを使う。
- エディター内で共有する既存の編集状態・操作は、型付き`provide/inject`を第一候補とする。
- 提供するAPIは「領域編集」「カード画面への外部操作」等の利用目的で絞り、親の全変数を一つの巨大オブジェクトにしない。
- 共有APIを作る場合、必要な参照と操作関数を渡す。資源の所有権やストア全体を不用意に渡さない。
- 子ごとに`useCardEditor()`を呼ばない。現在の実装では呼び出すたびに独立した状態と履歴ができる。
- Piniaへ履歴や全機能を移すことは今回の前提にしない。

候補の構成:

```text
CardEditor（全体の初期化・保存・画面切り替え・終了）
├─ 編集状態と操作を共有する窓口（既存インスタンスを提供）
├─ CardEditingWorkspace（カード編集UIとその連携）
│  ├─ CardCanvas
│  └─ Inspectorと領域編集関連UI
├─ CardList（配置・所属は工程0で判断）
├─ AssetEditor
└─ PrintLayoutWorkspace
```

共有窓口は新しい状態の複製ではない。名前・ファイル構成・提供範囲は依存調査後に確定する。
CardListには一括OCR、翻訳、書き出し、カード追加等の全体操作があるため、Canvasと同時に移すことを必須にしない。

## 共通の進め方

1. 現在の利用者、更新経路、寿命を確認する。
2. 現行動作を固定する回帰テストを先に追加し、変更前に通す。
3. 一つの所有境界・更新経路ずつ変更する。
4. 対象テストで確認し、工程の区切りで全体検証する。
5. 効果と残った依存を記録し、適切な粒度でコミットする。

これは既存動作を先にテストで固定してから構造を変える、TDDに近い進め方とする。
テスト失敗時は原因を確認し、期待値の緩和やskipで通さない。
不具合が見つかったら分割を止め、再現テストと修正を別コミットにまとめ、成功後に分割を再開する。
既に合意した範囲の不具合修正は都度の承認待ちにしない。仕様が不明な点は確認する。

親はWorkspaceを条件付きで破棄せず、Workspace内部の既存 `editor-layout` に `v-show` を適用する。
領域ダイアログは画面往復で隠れない従来の条件を維持する。

### 共有境界と残す接続

`cardEditingContext.ts` に編集・描画資源・OCR・翻訳の4つの型付きprovide/injectを定義した。
既存インスタンスを一度だけ生成する構成を維持し、Workspace内で履歴やWorkerを再作成しない。
編集APIから保存・カード切替操作を、描画資源APIから解放操作を除き、親の全状態を一つの共有オブジェクトへまとめていない。

| 接続 | 現在の担当と判断 |
| --- | --- |
| 本文・座標・マスク・保護領域・選択 | Workspace／CardRegionInspectorが編集APIへ直接接続。親へのイベント取次を削除 |
| Canvas API | Workspaceが登録・解除。画像書き出し・候補確定は既存の同一Refを参照 |
| CardList | プロジェクト全体の操作として親に残し、cardsスロットに配置。グリッドの直接の子を維持 |
| 一括翻訳の説明・操作 | 親のheaderスロット。カード一覧と共通の全体処理を利用 |
| OCR候補パネル | 一括OCRの確定・破棄と関連するため親のcandidatesスロット。Canvasの候補選択・移動はOCR共有APIを使用 |
| フォントUI | 資源の復元・削除・保存が全体側にあるためfontsスロット。領域のフォント指定はCardRegionInspector内 |
| 印刷設定UI | 複数カードへの適用・保存が全体側にあるためprintスロット。Canvasでの範囲変更のみWorkspaceから通知 |
| 配置雛形 | 保存する共有設定と編集カードの両方に関わるためlayout-toolsスロット。追加の責務分離は引き続き評価 |
| 原文アイコン | OCRとの連携を伴う全体側の操作窓口を参照。ダイアログの所有整理は残工程 |

親とWorkspaceの境界は3 props（visible、hasCardList、printArea）、3イベント（image、diagnostic、updatePrintArea）、6機能スロット。
開始時に親が持っていたCanvas 12・RegionInspector 21・RegionList 4のイベント接続はWorkspace配下へ移り、親には画像取込・診断通知・印刷範囲更新の3イベントを残した。
これは境界の接続数の比較であり、内部のイベント総数が同数減ったという意味ではない。

## OCR終了後の継続防止（2026-09-16）

最終回帰項目の確認で、選択領域OCRの画像前処理がエディター終了後に完了すると、終了したWorkerへ認識を開始する問題を再現した。
認識の遅い成功・失敗も、古い画面の通知タイマーや診断ログを更新していた。
前処理／認識それぞれの成功・失敗の4ケースを、終了後に別エディターを開く条件で追加し、修正前にすべて失敗することを確認した。

`useEditorOCR` が終了を記録し、各待機後・進捗通知・エラー通知・補正結果の反映を無効化する。
終了時に実行状態と候補を解除し、Worker本体のdisposeは引き続き全体側が一度だけ担当する。
これは構造変更とは独立した不具合修正。全78ファイル・497テスト、型検査、lint、`git diff --check`が成功した。
