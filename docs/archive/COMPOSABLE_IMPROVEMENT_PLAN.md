# コンポーザブル活用の改善案

作成日: 2026-09-16
状態: 完了（最終監査: 2026-09-16。公開停止中のPDFページへの接続は再公開時の別作業）

末尾の最終監査を現状の判定とする。途中の実装記録にある残工程・テスト数は、その時点の履歴。

## 目的

機能の追加・修正時に確認する範囲を狭め、状態の更新と非同期処理の終了を追いやすくする。
ファイル数や行数ではなく、責務・状態の所有者・依存関係が明確になったかで改善を判断する。

## 現状の評価

カード編集では、コンポーザブルの強みを既に活かせている。

- [useCardEditor](../../app/composables/useCardEditor.ts) は選択領域、編集操作、カード別のUndo／Redoをまとめている。
- [usePreviewDeferral](../../app/composables/usePreviewDeferral.ts) は描画の延期、対象変更の監視、タイマー解除を担当する。
- [useUnsavedChanges](../../app/composables/useUnsavedChanges.ts) はカードとPDFの両画面で離脱確認を共通化している。
- [usePrintPreviews](../../app/composables/usePrintPreviews.ts) は描画処理を外から受け取り、状態と画像URLの寿命を管理する。
- `tests/composables/` に履歴、資源管理、離脱確認などのテストがある。

一方、[PdfEditor.vue](../../app/features/pdf/PdfEditor.vue) はプレビュー、OCR、領域編集、読み込み、書き出しを一つのscriptに持つ。
[CardEditor.vue](../../app/components/CardEditor.vue) にも、多数の処理中フラグと機能間の接続が残っている。
[useProjectCards](../../app/composables/useProjectCards.ts) など、親から多数のRefやコールバックを受け取る箇所は、状態の所有範囲を再検討できる。

これはコードを読んだ設計上の評価であり、本提案の作成時にはテストを実行していない。

## 改善によるメリット

| 改善 | 開発・保守への効果 | 利用者への効果 |
| --- | --- | --- |
| PDF編集を責務ごとに分ける | プレビュー修正時にCSV入出力や領域編集まで読み解く必要が減る | 修正の影響範囲を抑えやすくなる |
| 処理中フラグを担当機能に集める | 開始・成功・失敗・終了の更新経路が追いやすくなる | 処理中表示の解除漏れや操作競合を防ぎやすい |
| 非同期処理と後片付けをまとめる | 古い結果の無効化と資源解放を一か所で確認できる | 連続操作や画面切替時の不具合を防ぎやすい |
| 親から渡す依存を減らす | 親と複数のコンポーザブルを同時に直す場面が減る | 機能追加後の動作を安定させやすい |
| 機能単位で検証する | 画面全体を組み立てずに失敗・中断・競合を再現しやすい | 不具合の発見と修正を早められる |
| 一緒に変更するファイルを近くに置く | 画面・状態管理・テストを機能単位で探せる | 関連箇所の修正漏れを防ぎやすい |

分割だけで実行速度やメモリ使用量が改善するわけではない。性能改善が必要な場合は別途計測する。
上記は期待する効果であり、分割後の検証で確認する。

## 優先順位と進め方

### 1. PDFプレビューを分離する

最初の候補は `usePdfPreview`。状態・非同期処理・資源の寿命がまとまっており、小さな範囲で効果を確かめやすい。
抽出時の配置は、後述のコロケーション計画の小さな試行と合わせて決める。

担当するもの:

- プレビュー画像とObject URL、表示中ページ、読み込み状態。
- ページ画像の生成と読み込み、最新要求だけを採用する制御。
- PDF差し替え時・画面終了時の要求無効化と資源解放。
- 現在の要求に対応するエラー状態。

PDF解析やページ描画そのものは既存サービスに残す。領域の選択や編集モードの切り替えは画面側の責務とし、プレビュー採用後に連携する。
描画サービスが処理中断を提供しない場合、結果の採用を止めることと処理自体の中止を区別する。

受け入れ条件:

- [x] ページを連続変更しても、最後の要求の画像だけが表示される。
- [x] 古い要求の成功・失敗で、現在の画像・エラー・読み込み状態が上書きされない。
- [x] PDF差し替えや画面終了後に、古い画像を採用しない。
- [x] 置換・失敗・終了で、不要なObject URLを解放する。
- [x] ページ採用後の領域選択と編集モードの動作を維持する。

既存の競合対策を移す際に不足が見つかった場合は、再現テストを用意し、挙動修正と分割を区別して記録する。

### 2. カード編集の状態の所有者を整理する

各Refについて、作成・更新・参照・リセットする箇所を確認する。
単一機能だけが更新する状態は、その機能のコンポーザブル内へ移し、親には必要な状態と操作を返す。

複数機能が共有するOCR実行状態や処理中判定は、個別に複製せず所有者を一つにする。
親の `projectBusy` のような集約値と、個々の機能が持つ実行状態の依存方向を整理し、循環依存を避ける。

受け入れ条件:

- [x] 状態の所有者とリセットの契機を説明できる。
- [x] 親から渡す可変Ref・コールバックが減り、別の巨大な引数オブジェクトへ移しただけになっていない。
- [x] 成功・失敗・中断後に、処理中状態が適切に戻る。
- [x] カード切替、保存、OCRの排他制御とUndo／Redoを維持する。

この工程は [CardEditingWorkspace分割・状態と操作の所有整理計画](./CARD_EDITOR_WORKSPACE_PLAN.md) と重なるため、カード側の具体的な作業は同計画にまとめ、二重に進めない。

### 3. PDFの残りの機能を段階的に分離する

プレビュー分離の効果を確認した後、次の候補を依存関係に応じて一つずつ検討する。

| 候補 | 主な責務 |
| --- | --- |
| PDFの読み込み・セッション管理 | 解析、プロジェクト復元、処理中断、文書差し替え |
| PDF領域編集 | 選択、原文下書き、除外、結合・分割 |
| PDF OCR | 実行状態、結果の採用、終了処理 |
| PDF入出力の画面制御 | CSV・PDF書き出しの実行状態と通知 |

候補ごとに、状態と操作をまとめる価値があるか確認する。純粋な計算や入出力処理は、引き続き `utils`・`services` に置く。

## コロケーションの改善計画

### 目的と配置方針

現在は `components`・`composables`・`services`・`tests` と技術的な役割で配置されている。
種類ごとには探しやすいが、一つの機能の変更で複数のディレクトリを行き来する。
一緒に変更する画面・状態管理・テストを近くに置き、機能ごとに確認する範囲を絞る。

| 対象 | 配置方針 |
| --- | --- |
| PDF専用の画面・コンポーザブル | `app/features/pdf/` に段階的にまとめる |
| カード編集専用の画面・コンポーザブル | Workspace分割計画と合わせて機能境界を決め、カード編集配下への配置を検討する |
| `useUnsavedChanges` など複数画面で使う処理 | 共通の場所に残す |
| 複数機能から使う計算・サービス・型 | 既存の共有ディレクトリに残す |
| 機能専用の単体テスト | 対象コードへの隣接配置を試す |
| 複数機能にまたがる連携テスト・E2E | `tests/` に残す |

純粋な計算や入出力は、配置を変えてもコンポーザブルへ変換しない。
専用サービスの移動は実際の利用箇所を確認して判断し、初回の試行では既存サービスを参照する。
ファイルの近さに加え、状態の所有と依存方向を整理する。機能間で互いの内部ファイルを参照する構成は避ける。

### 工程A: PDFプレビューで小さく試す

最初は新しい `usePdfPreview` とそのテストを隣接配置する。
既存の `PdfEditor.vue` から明示的にimportし、画面全体の移動を先行させない。

```text
app/features/pdf/
  usePdfPreview.ts
  usePdfPreview.test.ts
```

- [x] 関連コードの利用箇所を調べ、PDF専用と共有を区別する。
- [x] `usePdfPreview` の分離と隣接テストを一つの試行として実施する。
- [x] 移動・追加したファイルは明示的にimportし、従来の自動importに依存した参照を確認する。
- [x] Vitestのテスト探索と実行環境を確認し、隣接テストが実際に実行されることを確かめる。
- [x] 型検査・lintの対象に隣接テストが含まれるよう確認し、必要な設定だけを変更する。
- [x] アプリのビルドにテストコードやテスト用依存が取り込まれないことを確認する。

現状の `vitest.config.ts` は `include` を限定していないため、移動だけを理由に探索設定を追加しない。
`tests/tsconfig.json` の `include` に `../app/features/**/*.test.ts` を追加し、隣接テストを明示的に型検査する。DOMを使うテストは既存テストの実行環境指定も確認する。

### 工程B: PDFの画面と専用部品をまとめる

工程Aで探索性と検証に問題がないことを確認してから、PDF専用の画面・部品を移す。
次は到達構成の例であり、すべてを同時に移すことは前提にしない。

```text
app/features/pdf/
  PdfEditor.vue
  PdfPreviewCanvas.vue
  usePdfPreview.ts
  usePdfPreview.test.ts
```

- 対象外（再公開時の作業）: ページから機能の入口となる `PdfEditor.vue` を明示的にimportする。現在の `/pdf` は公開停止中の案内ページであり、再公開を決めるまで接続しない。最終監査でも未接続であることを確認した。
- [x] 専用部品は機能内から参照し、共有部品は既存の共通配置を利用する。
- [x] テストのimport・mock・stubとドキュメントのリンクを移動先に合わせる。
- [x] ファイル移動と挙動変更を区別できる単位で進める。
- [x] PDF読み込み、ページ切替、OCR、編集、書き出しの既存の接続を確認する。

### 工程C: カード編集への適用を判断する

[CardEditingWorkspace分割・状態と操作の所有整理計画](./CARD_EDITOR_WORKSPACE_PLAN.md) に配置方針を組み込み、Workspace分割と同じタイミングで移動範囲を決める。
OCR・印刷などの下位ディレクトリは、関連ファイルの数と依存関係が必要とする場合に設ける。
共通コンポーザブルや共有サービスをカード側へ取り込まず、PDFで得た効果を確認してから適用範囲を広げる。

### 受け入れ条件

- [x] PDFプレビューの実装と単体テストを同じディレクトリで確認できる。
- [x] 機能専用と共有の配置基準が明確で、循環依存や重複実装を増やしていない。
- [x] 移動したコードのimport、自動importへの依存、テスト、文書リンクを更新している。
- [x] 隣接テストの実行・型検査・lintと、アプリのビルドが成功する。
- [x] 配置変更に伴う画面操作や公開APIの意図しない変更がない。

完了時には、ある機能の変更で参照するディレクトリと外部依存がどう変わったかを記録する。
探索や変更の負担が減らない場合は、全体へ展開せず配置の粒度を見直す。

## 設計上の方針

- 保存する文書はストア、カード編集履歴は `useCardEditor`、ブラウザ資源は `useProjectRuntime` という既存の境界を尊重する。
- 同じ状態を複数箇所に持ってwatchで双方向同期する構成を避ける。
- 再利用先が一つでも、状態・操作・監視・寿命をまとめられる分離には価値がある。
- 共通化は実際に共通する責務に限る。カードとPDFの異なる保存形式を無理に統一しない。
- フックによる自動解放か、所有者による明示的な解放かを決め、呼び出し順序を含めて明記する。
- 引数やファイルが増えるだけで理解する範囲が狭まらない抽出は見直す。

## 検証と完了の判断

1. 対象の現在の動作と既存テストを確認する。
2. 最新要求の採用、失敗、中断、資源解放など、重要な動作を検証するテストを補う。
3. 一つの責務ずつ抽出し、対象テストを実行する。
4. 親との接続をコンポーネントテストで確認する。
5. 実装変更の完了時に `pnpm test`、`pnpm typecheck`、`pnpm lint`、`pnpm build` を確認し、変更した画面操作も検証する。

完了時には、移した状態、削減できた依存、残した依存と理由、検証結果を記録する。
機能を変更するために読む範囲が狭まり、状態の更新元と非同期処理の終了経路が明確になっていることを重視する。

## 実装記録: 2026-09-16（処理中フラグの所有）

`savingProject`、`openingProject`、`addingCards`、`loadingCardId`、`exportingCards` を担当composable内で生成し、読み取り専用Refを返すようにした。
開始・終了は既存の処理内で行い、正常終了、エラー、途中returnでもfinallyで解除する。親から渡す可変Refを5つ削減した。

`useProjectActivity` は同じエディター寿命の4つの状態をsetup時に登録し、読み取りだけで `busy` を計算する。
各機能の値の複製・同期watch・新しい処理中フラグは作らない。
各機能は `busy` を実行開始のガードで読み、集約側は各機能の状態だけを読むため、computed同士の循環を作らない。
一括書き出しは内部でカード切替を使うため集約に含めず、従来の専用ガードを維持した。
型参照はカード用集約APIへのtype-only importで、実行時の依存はVueだけ。

保存と切替の相互排他を成功・失敗の4ケースで変更前に固定し、追加・読込の開始／終了／取消も4ケース追加した。
既存の終了後の結果破棄、カード別Undo/Redo、OCR中の切替禁止、一括書き出し後の元カード復帰も成功している。
全79ファイル・508テスト、型検査、lint、ビルド、Playwright全7ケースが成功した。

## 実装記録: 2026-09-16（PDF項目編集）

残る候補を確認し、選択・原文下書き・除外・結合・分割を先に `usePdfEntryEditing` へ分離した。
原文修正や結合・分割では訳文を無効化し、除外設定も引き継ぐため、これらを同じ操作の中で追える単位にした。
純粋な座標・文字項目の変換は既存PDFサービスに残している。

| 状態・依存 | 担当 |
| --- | --- |
| 選択ID・原文下書き・除外ID | `usePdfEntryEditing` が生成・更新・文書切替時のresetを所有 |
| 解析文書・訳文Map | 読込・CSV・OCRとも共有する同一Refを利用。コピーや同期watchは追加しない |
| 表示中ページ | `usePdfPreview` の読み取り専用Refを参照 |
| 選択に伴う下書き更新 | 項目編集composableのwatch。コンポーネントと同じスコープで終了 |

## 実装記録: 2026-09-16（PDF実行状態の所有と残る候補の評価）

`usePdfProcessing` が解析・復元・書き出しの処理中判定、表示ラベル、進捗、AbortController、終了時の解放を所有する。
親は読み取り専用状態と `begin`／`cancel` を受け取り、各操作は返された要求の `reportProgress` と `finish` を使う。
要求ごとの識別により、古い進捗や重複したfinallyが次の処理を上書きしない。
キャンセル直後は実処理が完了するまで排他状態を維持する。画面終了時はsignalを中止し、表示状態を解除して新しい開始を拒否する。
