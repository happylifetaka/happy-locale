# CardEditor.vue追加改善計画

作成日: 2026-09-16
状態: 計画作成済み・実装未着手

## 目的と基準

[前回の分割計画](./CARD_EDITOR_REFACTORING_PLAN.md)で、`CardEditor.vue`を3,993行から1,936行へ縮小した。
次は残った処理の分割に加え、親が中継している共有状態とイベントを整理する。

改善の基準は以下とする。

- 機能を修正する際に読む範囲が絞れる。
- 状態の所有者と更新経路が明確である。
- 親を経由するだけのprops・イベントが減る。
- 編集履歴、保存形式、非同期処理、画面操作を維持する。

直前の検証結果は全437テスト、型検査、lint、ビルド成功。
Playwrightの3テストとユーザーによる日本語IMEの手動確認も成功している。
実装開始時には作業ツリーとテストを再確認する。

## 状態の所有と更新ルール

| 状態・処理 | 所有者 | 方針 |
| --- | --- | --- |
| 保存する文書・カード一覧・共有設定 | `useProjectStore` | 既存の保存経路を維持 |
| 領域本文・座標とUndo/Redo | `useCardEditor` | 本文や領域を別ストアから直接更新しない |
| 画像・フォント・Object URL | `useProjectRuntime` | 資源の所有と解放を維持 |
| 複数の表示部品が使う編集ツール状態 | 新規`useEditorToolsStore`候補 | 小さく試し、効果を確認して拡張 |
| ダイアログ内だけの入力途中の値 | 各コンポーネント | 局所的な状態はその場で管理 |
| 読込・OCR等の非同期状態 | 各composable | 実行の中止・終了後の無効化も同じ責務で管理 |

Piniaに全機能を集める巨大なエディターストアは作らない。
既存のローカルrefとストアをwatchで双方向同期させず、状態の所有元を一つにする。
ストアの状態を分割代入する場合は`storeToRefs`でリアクティブ性を維持する。

## 共通の作業手順

1. 現状の動作、変更経路、初期化・終了タイミングを確認する。
2. 現行実装に回帰テストを追加し、変更前に通ることを確認する。
3. 重要なガードは一時的な変更でテストの検出力を確認し、必ず復元する。
4. 一つの責務・一つの更新経路ずつ変更する。
5. 対象テストと必要な全体検証を実行する。
6. 結果・行数・依存の変化を記録し、適切な単位でコミットする。

不具合が見つかったら分割を止め、再現テストを用意して修正する。
修正は分割と別のコミットにまとめ、テストが成功してから分割を再開する。
既に合意した範囲の不具合修正は都度の承認待ちにしない。仕様が不明な場合だけ確認する。
期待値の緩和やskipで失敗を解消しない。

## 工程0: 依存とライフサイクルの整理

- [ ] ブラシサイズ、ブラシモード、マスク編集、保護領域編集について、参照箇所と変更箇所を列挙する。
- [ ] カード切替、領域選択変更、画面切替、プロジェクト読込、画面終了時の現在のリセット規則を記録する。
- [ ] 状態を保持する項目とリセットする項目をテストで固定する。
- [ ] 同時に複数のCardEditorが存在する利用経路がないか確認する。存在するなら単一の共有ストアにせず、エディター単位の所有範囲を設計する。

受け入れ条件: Pinia導入によって状態の寿命やリセット規則が暗黙に変わらない。

## 工程1: 編集ツール状態をPiniaで共有する小さな試行

最初の対象はブラシサイズ・追加／消去モードと、マスク／保護領域の編集モードに限定する。
ストア候補は`app/stores/editor-tools.ts`、利用関数名は`useEditorToolsStore`。

- [ ] マスク編集と保護領域編集の排他制御、ブラシ設定のCanvasへの反映を連携テストする。
- [ ] カード・領域・画面の切替と終了後の再表示で、工程0の保持・リセット規則をテストする。
- [ ] 単純なブラシ設定は状態として公開し、排他制御は`startMaskEditing`等のactionにまとめる。
- [ ] CanvasとInspectorの接続箇所をストア参照へ移し、親の中継を削除する。
- [ ] テストごとにPiniaを独立させ、前のテストの状態を持ち越さない。
- [ ] 実際のCanvasとInspectorが同じ状態を使うことを検証する。親の子スタブだけではこの接続を保証しない。
- [ ] 接続削減量と依存の増加を評価し、残りの状態を移すか判断して記録する。

部品の再利用性が必要な場合は、ストアを読む機能別コンポーネントから表示部品へ渡す構成も候補とする。
propsの束をそのまま中継するだけのラッパーは追加しない。
画面終了時のストアリセットは、その状態を所有するエディター側が一度だけ行う。

受け入れ条件: 親の中継が減り、編集本文・Undo/Redo・資源管理への依存を追加せず、表示の連携も維持できる。

## 工程2: v-modelと操作イベントを整理する

工程1で残った親子の値同期を対象とする。ストアで直接共有した項目に、重ねてv-modelを追加しない。

| 接続の種類 | 表現 |
| --- | --- |
| ズーム等、単一の値の同期 | `v-model:zoom`等 |
| 保存・削除・認識などの操作要求 | `@save`、`@remove`、`@recognize`等 |
| 他のモードや状態も変更する操作 | 明示的なactionまたは操作関数 |
| 確定前のダイアログ入力 | 子が下書きを持ち、確定イベントで反映 |

- [ ] 単純な代入だけのイベント接続を洗い出し、親子を同時にv-modelへ変更する。
- [ ] `defineModel`等を使う場合、親と子で初期値・必須性・型が食い違わないようにする。
- [ ] 領域本文の入力は現在の履歴更新・IME・描画遅延の経路を維持する。
- [ ] 取消可能な入力が確定前に親へ反映されないことを確認する。
- [ ] Playwrightで編集・タブ切替を確認する。IMEの処理経路を変更した場合は実IMEも再確認する。

受け入れ条件: 接続の意味が読み取りやすくなり、代入によって更新時の検証や副作用を飛ばさない。

## 工程3: 印刷設定を分離する

候補: `useEditorPrintSettings`。用紙設定、カードの印刷範囲・DPI、未設定カードへの一括適用を扱う。
印刷レイアウト画面への移動は画面構成側に残す。

- [ ] サイズの異なるカードへ画像サイズ比で範囲を適用するテストを追加する。
- [ ] 設定済みの範囲・DPIを上書きせず、片方だけ未設定の場合は必要な項目だけを補うことをテストする。
- [ ] 対象カードだけの更新、範囲解除、保存への反映をテストする。
- [ ] 必要な文書参照・更新操作だけを受け取る形で抽出する。

## 工程4: 画像読込を分離する

対象は形式・容量・寸法の検証、load/decode待ち、失敗時・終了時の解放。
純粋な画像読込サービスと画面の終了管理を分けるか、専用composableにするかは依存を確認して決める。
カード画像の採用と領域候補の初期化は、読込の成功後に呼出元が行う。

- [ ] 不正形式・容量超過・寸法超過・load失敗をテストする。
- [ ] load成功後のdecode失敗でも現在の継続動作を維持することをテストする。
- [ ] 読込中の終了でURLを解放し、終了後に採用・通知しないことをテストする。
- [ ] カード画像とアセット元画像の両経路を確認する。
- [ ] 読込側からruntimeへ所有を渡す時点を明示し、二重解放・解放漏れを防いで抽出する。

## 工程5: 領域編集の操作を分離する

候補: `useRegionEditing`。まず削除・分割・移動を一単位として扱い、マスク・保護領域の操作は依存を確認して追加する。
実際の編集履歴への反映は`useCardEditor`に委ねる。

- [ ] 削除確認の取消・確定、分割後のUndo/Redoをテストする。
- [ ] 分割確認中のカード・対象領域の変更を検知し、古い結果を拒否することをテストする。
- [ ] 領域移動・リサイズ時のマスク、保護領域等の座標変換を確認する。
- [ ] ブラシの1操作とUndoの単位が維持されることを確認する。
- [ ] 原文アイコン指定を同じ機能へ含める場合は、候補を開いてから対象が変わるケースもテストする。
- [ ] UIモード状態は工程1の所有元を使い、重複した状態を持たずに抽出する。

## 工程6: 用語集と既存訳再利用を分離する

用語集の編集と既存訳の適用は別の責務として扱う。候補は`useEditorGlossary`と`useTranslationReuse`。

- [ ] 空入力、前後空白、正規化後の重複、更新時の自分自身の除外をテストする。
- [ ] 用語集・他カードからの候補取得と、適用時のUndoをテストする。
- [ ] 確認中のカード・原文・訳文変更後に古い候補を適用しないことをテストする。
- [ ] 既存の純粋関数のテストを重複させず、画面・ストア・履歴の連携を補って抽出する。

## 工程7: 画面状態と機能単位のコンポーネントを再評価する

ここは工程1〜6の結果を見て判断する段階であり、すべての状態をPiniaへ移すことは必須にしない。

- [ ] ズーム、表示モード、選択タブについて共有の必要性と状態の寿命を確認する。
- [ ] 必要なものだけストアまたは専用composableへ移す。部品内で完結する状態は局所化する。
- [ ] CanvasとInspectorをまとめる編集画面コンポーネント、用語集の表示と操作をまとめるコンポーネントの効果を比較する。
- [ ] 見た目だけでなく、その機能の状態と操作も一緒に移せる境界を選ぶ。
- [ ] 表示切替によるアンマウントが画像・フォント・履歴・非同期処理の寿命を変えないことを確認する。
- [ ] 効果が小さい分割は採用せず、理由を記録する。

## 検証とコミット

```bash
mise exec -- pnpm test
mise exec -- pnpm typecheck
mise exec -- pnpm lint
mise exec -- pnpm build
mise exec -- pnpm test:e2e
git diff --check
```

各抽出後に対象テストと全体のテスト・型検査・lint・ビルドを実行する。
UI接続や状態の寿命を変更した工程ではPlaywrightも実行する。
OSの日本語IMEとFile System Access APIの権限操作は自動テストの保証範囲と分け、変更に関係する場合だけ手動確認を依頼する。

原則として「回帰テスト追加」「必要なら不具合修正」「責務の抽出」を区別してコミットする。
