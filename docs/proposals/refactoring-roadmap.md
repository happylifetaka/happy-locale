# リファクタリング・ロードマップ

作成日: 2026-09-20。調査基点: `d0146b9`。状態: 実施中（P0の自動回帰・性能基準を取得。P1の構造整理・自動検証を実施。P2以降は未完了）。

進捗と確認範囲は[回帰基準](../verification/refactoring-baseline.md)へ記録する。利用者の指示により、計画・回帰基準・機能抽出を適切な粒度でコミットする。push・公開は行わない。

## 1. 目的と優先順位

利用者の希望は「既存機能を保ち、変更・テストしやすくする」を最優先に、拡張性・性能も改善すること。

全面書き換えではなく、既存の状態分離を維持して、変更が波及しやすい境界から小さく整理する。見た目・保存形式・OCR結果を変える作業は、構造整理と別の変更として扱う。

この文書は技術的な整理計画であり、[機能ロードマップ](../ROADMAP.md)の機能完了状態を変更しない。ゲーム画像・個別検証結果・専用設定は公開文書へ転載しない。

## 3. Nuxt・Vue公式資料からの判断材料

以下の「採用方針」はこのプロジェクトへの提案であり、公式資料がHappyLocaleの配置を指定しているわけではない。参照日: 2026-09-20。

| 公式資料で確認した事項 | HappyLocaleでの採用方針 |
| --- | --- |
| Nuxtは`app/`以下の規約ディレクトリを持つ。[Directory structure](https://nuxt.com/docs/4.x/directory-structure) | pagesはルート接続、featuresは機能内部、servicesは処理境界という既存方針を発展させる |
| composablesの配置はリアクティビティを自動付与するものではない。自動走査は既定でトップレベル。[Composables](https://nuxt.com/docs/4.x/directory-structure/app/composables) | 機能専用composableをfeaturesへ移す場合は明示import。走査範囲を全体へ広げない |
| Nuxtは`#imports`による明示importも提供する。[Auto-imports](https://nuxt.com/docs/4.x/guide/concepts/auto-imports) | 共有TSサービスはNuxtコンテキスト非依存。機能間依存は明示し、Vue APIの自動importまで一括廃止しない |
| Vueのcomposableは関心ごとの状態を分離できる。DOM副作用はブラウザのライフサイクル内で行い、後始末が必要。[Vue Composables](https://vuejs.org/guide/reusability/composables) | 画面スコープの操作はcomposable、純粋計算は通常関数。Workerや画像資源の解放責任を一箇所へ |
| NuxtのuseStateはシリアライズされ、モジュール直下の共有refにはSSR上の注意がある。[State management](https://nuxt.com/docs/4.x/getting-started/state-management) | Blob・Worker・ファイルハンドルを共有シリアライズ状態へ移さない。PiniaからuseStateへ全面移行しない |
| PiniaはNuxt 3/4向け統合を提供する。[Pinia Nuxt](https://pinia.vuejs.org/ssr/nuxt.html) | 既存`@pinia/nuxt`を維持。公式ページの表示系列とローカル依存系列が異なるため、新API採用時は導入版との互換性を別途確認 |
| Nuxt公式は通常の単体テストとNuxt環境テストを分ける構成を案内する。[Testing](https://nuxt.com/docs/4.x/getting-started/testing) | 全テストをNuxt起動必須にしない。必要なルート・runtimeConfig・注入のテストだけ追加する |
| Layersはコード・設定等をまとめて再利用できる。[Layers](https://nuxt.com/docs/4.x/directory-structure/layers) | 今回は導入しない。独立アプリ間の再利用要求が出た時点で再検討 |
| Vueは計測、コード分割、大規模データの浅いリアクティビティ、リスト仮想化等を説明する。[Performance](https://vuejs.org/guide/best-practices/performance) | 計測で効果を確認してから採用。既存shallowRefやOCRの動的importを再実装しない |

## 4. 目指す責務と依存方向

```text
pages / CardEditor（生成・接続）
  → features/cards（操作フロー、画面状態、用途別Context）
      → stores（保存可能な正規データの更新）
      → services（OCR、フォルダ、翻訳等の実行）
          → 純粋な変換・検証・幾何計算
      → runtime（ブラウザ資源の所有・解放）
```

- serviceや純粋関数からUI・composable・Piniaインスタンスを逆参照しない。
- UIの共有は既存Contextを活用するが、何でも取得できる巨大Contextにはしない。
- フォルダ名だけの一斉移動を目的にしない。機能を抽出するPRに関連する移動だけ含める。
- `app/types/editor.ts`がOCRサービス側の候補型を参照している点は、保存契約に必要な型とProviderの入出力型を分ける候補。ただし同じ型を重複定義しない。
- Storeは永続データ、履歴は編集セッション、runtimeは非JSON資源という所有関係を維持する。状態を減らすために履歴や候補の作業コピーを無条件に削除しない。
- 抽出先の名称は実装時に調整可能。巨大な`useEverything`への移動で完了としない。

## 5. 段階別ロードマップ

順序は P0 → P1 → P2 → P3 → P4 → P5 を推奨。性能の基準計測はP0で行い、改善は後段。各段階は独立した小さいPRに分ける。

### P0: 回帰基準と変更境界を固定する（最優先）

作業:

- 既存テストを操作ごとに対応付け、不足している境界テストだけ追加する。
- 保存失敗、初回保存、カード切替とUndo、OCR遅延結果、候補復元、印刷・画像出力の基準を固定。
- 公開可能な合成データでOCRの枠・文字列・信頼度・選択状態を比較できるfixtureを作る。私有画像の記録は`docs/local/`で管理。
- 同一ブラウザ・データで初期表示、カード切替、ドラッグ、保存差分計算、OCR補正時間、反復操作後の資源数・メモリを計測する。
- 現行のシリアライズ出力を基準にし、構造変更による差を検出する。

完了条件: 保護する操作とテストの対応表、再実行手順、性能基準値があり、失敗時にどの責務が壊れたか判別できる。既存テストの緑だけを全操作確認とはしない。

規模目安: 1〜2 PR。新機能を追加しない。

### P1: カード画面の操作フローを分離する

進捗: 候補レビュー、診断・通知・ショートカット、画像・プロジェクト採用の抽出とContext公開型の明示化を実施済み。対象の単体・画面接続・型検査、主要フローのブラウザ・静的生成の結果は[回帰基準のP1記録](../verification/refactoring-baseline.md#p1-a-候補レビュー操作の抽出)を参照。実フォルダ・実フォントの手動確認や公開確認を完了した意味ではない。

作業:

- `CardEditor`内の候補の表示・退避・確定・破棄を、カードIDを受け取る候補レビュー操作へ抽出。
- 画像・プロジェクトの採用処理を、既存session/navigation/runtimeの所有関係を守って整理する。新規と既存プロジェクトの切替を混同しない。
- 診断ログ、通知タイマー、ショートカットは画面スコープの独立composableにする。
- 抽出する機能専用コードは`features/cards/`配下へ。保存・OCR等の既存composableを一度に全移動しない。
- `ReturnType`への依存は、変更が波及するContext・外部境界だけ小さなinterfaceへ置き換える。

完了条件: 親は生成・接続・表示切替が中心。候補確定を親画面全体なしでテストでき、初回保存・カード切替後も候補と履歴が保たれる。画面の見た目・公開props/eventsは原則不変。

規模目安: 2〜3 PR。リスク: 生成順・同じインスタンスの共有・カードIDの取り違え。

### P2: OCRの実行経路・規則・設定を分離する

進捗: 1画像の共通検出サービスと単体・一括の接続、出力一致・非同期破棄・実Workerの検証を実施。候補生成の段階分割、残る規則・保存候補型の分離は未完了。[P2-aの記録](../verification/refactoring-baseline.md#p2-a-1画像の検出サービスを共通化)を参照。

作業:

- 1画像の検出を`detectRegions`相当のサービスへ集約し、単体・一括は画像の取得、進捗、結果の保存・確認だけ担当する。
- 入力は画像・寸法・Provider・設定・対象有効性チェック、出力は候補・必要な診断情報。サービスからStoreを更新しない。
- `candidates.ts`をフィルタ、見出し補正、行結合、候補枠生成に分け、実行順と既定値は変えない。
- [条件一覧](../verification/ocr-detection-conditions.md)を基に、ゲーム形式に依存し得る規則を明示的な設定・内部ポリシーへ整理する。細かい数値をすべてUIへ露出しない。
- 保存する候補の型をProviderの実装型から分離。Provider内部のデータやCanvasは永続化しない。
- 非同期対象確認とfinallyでの解放を共通契約にする。ただしProviderに中断APIがない状態で「実行を即停止できる」と扱わない。

完了条件: 同じ画像・同じOCR出力から、単体と一括で同じ候補が生成される。既定設定の枠・順序・文字列・信頼度・チェック状態が回帰基準と一致する。失敗・破棄後に古い結果が適用されない。

規模目安: 2〜3 PR。画像処理結果を改善するPRは別途。外部JSON・UIを作る場合はP2bとして後述の判断が必要。

### P3: 保存・履歴・非同期処理の契約を明確化する

作業:

- 保存形式の移行、値の検証、参照整合性、書き出しを内部モジュールへ分離し、既存の公開関数は窓口として維持する。
- フォルダI/Oと「保存開始時点の内容を確定し成功した版だけ承認する」手順を分ける。バックアップ・画像先行書込・成功後削除の順は維持する。
- Storeへの書込窓口、編集履歴からの同期、候補の作業コピーの反映を文書化してテストする。
- 処理中フラグは一斉に置換せず、重複する対象ID・世代の確認を抽出できる箇所だけ共通化する。

完了条件: version 0/省略/1/2から3への移行、未知version拒否、不正候補拒否、保存中の変更維持、途中失敗時の参照整合性、カード別Undoが保たれる。構造整理だけなら保存versionを上げない。

規模目安: 2〜3 PR。最もデータ損失リスクが高いため、Canvas変更と同じPRにしない。

### P4: Canvasの入力・描画を分離する

作業:

- 座標変換、矩形正規化、ヒット判定、移動・リサイズ計算を純粋関数へ抽出する。
- 領域・候補・除外範囲・印刷範囲・ブラシの操作状態を整理する。共通化は同じ挙動が確認できた部分だけ。
- 編集用オーバーレイとカード本体描画を明確に分け、既存のプレビュー・書き出し共通render経路を維持する。
- pointercancel、lostpointercapture、画面破棄の終了処理を明示する。

完了条件: 複数倍率で同じ原画像座標に編集でき、1操作が1履歴単位になる。中断時にドラッグ状態が残らず、出力に選択枠・ガイドが混入しない。数値テストに加え実ブラウザで画面と出力を確認する。

規模目安: 2〜3 PR。この段階では描画アルゴリズムやフォントレイアウトを変更しない。

### P5: 計測結果に基づく性能改善とNuxt接続の検証

作業:

- P0の計測で重かった箇所を1つずつ改善する。候補はCanvas再描画集約、不要な全体差分計算、遅延UI読込、長い一覧の仮想化。
- Worker化・OffscreenCanvas・新キャッシュは、計測上の必要性と対応ブラウザの扱いを確認してから採用する。
- `@nuxt/test-utils`はNuxt固有の接続テストに限定して導入を評価する。既存Vitest 5等とのpeer dependency互換性を先に確認し、合わなければ既存Playwrightで検証する。依存更新を抱き合わせない。
- ルート遷移、runtimeConfig、サブパス配信、公開版の外部Endpoint無効化を実Nuxt環境で確認する。

完了条件: 同条件の前後計測で効果が確認でき、OCR結果・保存内容・操作感に回帰がない。採用しなかった最適化も理由を残す。「ファイルが小さくなった」を速度改善の証拠にしない。

規模目安: 計測次第で1〜3 PR。数値目標はP0の基準値取得後に設定する。

## 6. 共通の検証・リリースゲート

- 各PR: 変更責務に対応する単体・画面接続テスト、型検査、Lint、`git diff --check`。
- 統合時・push/PR: 現行CIの`test`、`typecheck`、`lint`、サブパス指定`build:static`。
- Nuxt配置・import・SSR境界・依存を変えたPR: 静的生成をローカルでも確認。
- UI接続・Canvas変更: 関連Playwrightと[手動確認](../MANUAL_TESTS.md)。実フォルダI/O・フォント・Canvasはモックの成功で代替しない。
- OCR変更: 公開可能な合成fixtureの比較と、利用者が管理する私有画像のローカル確認を分ける。私有素材をCIへアップロードしない。
- 各段階の成果は個別コミットで戻せるようにする。構造変更PRで保存形式を変えない。公開後に問題が出た場合は元の実装へ戻せる状態を維持する。
- コミット・push・公開はそれぞれ別の実行判断。今回の計画作成は公開反映を許可するものではない。

## 7. 今回は採用しない大きな変更

- Nuxtから別フレームワークへの移行、全体のSSR無効化。
- PiniaからuseStateへの全面移行、単一の巨大Store化。
- 全機能のNuxt Layers化、汎用DIコンテナ、新たな状態機械ライブラリの先行導入。
- OCR・ファイル処理をuseAsyncDataへ一律置換。ユーザー操作で開始するローカル副作用は別の責務として扱う。
- 保存形式の刷新、既存PDF実装の削除、ゲーム専用プロファイルの公開同梱。

## 8. 利用者への判断事項

| 項目 | 推奨案 | 状態・影響 |
| --- | --- | --- |
| 優先順位 | 保守性・回帰防止 → 拡張性 → 計測に基づく性能改善 | 利用者回答: 保守性優先だが全部対象 |
| 公開停止中のPDF翻訳 | 保持し、共通部分の変更に対する回帰確認のみ。内部再設計は別ロードマップ | 確認中。PDF内部まで含める場合は別段階を追加 |
| OCRプロファイル | P2では内部境界まで。ローカルJSONの検証・読込・切替はP2bへ | 確認中。UIまで含める場合は保存・共有方針も必要 |

P2bを実施する場合に追加で決めること: 設定を端末だけに保持するか、プロジェクトへ明示同梱できるか。端末限定は非公開管理しやすいが、別端末での結果再現に設定の再読込が必要。同梱は再現性が上がる一方、共有相手へ専用設定も渡る。自動同梱・外部送信は既定にしない。

## 9. 最初の着手単位

承認後はP0から開始し、続いて「候補レビュー操作の抽出」を最初の実装PRにする。現在のOCR精度や保存形式を変えずに、親画面への依存を減らせる範囲から始める。

本計画作成時に実施したのはコード・CI設定・公式資料の調査と文書確認。アプリ実装の変更、性能の実測、テスト全体の再実行、依存追加は行っていない。
