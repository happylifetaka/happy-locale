## 解決したい課題

OCR後も翻訳の入力や外部ツールとの往復に手間がかかる。アプリ内で原文から下訳を生成し、利用者が確認・修正して確定できるようにする。

目標は、利用者に翻訳APIの有料契約を求めず、カードのアセットタグや数字を維持した翻訳候補をまとめて作ること。翻訳品質と利用・配布条件を確認して採用を決める。

## 提案時点の実装

- [types.ts](../../app/services/translator/types.ts): 共通の `TranslationProvider` がある。
- [local.ts](../../app/services/translator/local.ts): 指定Endpointの `/translate` と `/health` を利用する。翻訳エンジン自体は内蔵していない。
- 公開用の静的ビルドでは外部Translation Endpointを無効にしている。
- デモの翻訳は同梱データを使う。
- 翻訳の一括確認、用語集、同一原文の既存訳再利用の基盤がある。

既存の翻訳候補の確認フローに新しいProviderを接続する。公開版でのブラウザ内翻訳と、ローカル起動時のサーバー接続を別の選択肢として扱う。

## 候補の比較

| 候補 | 利点 | 制約・採用前の確認 |
| --- | --- | --- |
| Chrome内蔵Translator API | 端末内で翻訳でき、別途翻訳サーバーを用意する必要がない。公開静的サイトへの組み込み候補 | 対応ブラウザ・端末・言語ペアの確認が必要。初回モデルダウンロードがある。Chromeの機能利用であり、OSSモデルを同梱する方式ではない |
| Argos Translateをローカル接続 | オフライン実行が可能。本体のライセンスはMITまたはCC0 | 別途セットアップが必要。言語モデルと依存ライブラリの条件は個別に確認する。既存Endpoint形式に合わせた接続層が必要 |

まずChrome内蔵翻訳を試作し、実際の英日カード文で品質と使いやすさを評価する。OSS構成が必要な場合や対応環境が合わない場合はArgos Translateを検証する。この順序は提案であり、採用決定ではない。

## 操作フロー

1. 翻訳方法としてブラウザ内翻訳を選ぶ。
2. 対応状況を確認し、初回のみモデル取得の説明と進捗を表示する。
3. 未翻訳領域を対象に、既存訳の再利用候補を確認する。
4. 残りの領域の下訳を生成する。進捗を表示し、キャンセル・失敗分の再試行を可能にする。
5. 原文・訳文候補・元画像を並べて確認する。数字やアセットタグの不整合を表示する。
6. 利用者が選択した候補だけを適用する。既存の手修正済み訳文は自動で上書きしない。

非対応環境やモデル取得失敗時も、手動入力・CSV・既存訳の再利用を使える状態に保つ。

## 実装方針

### Providerの追加と公開版の扱い

Chrome内蔵翻訳用のProviderを追加し、APIの存在確認に加えて言語ペアの利用可否を判定する。初期化・モデル取得は利用者の操作を起点に行う。SSR時にはブラウザAPIへアクセスしない。

外部Endpointの公開版無効化は維持し、ブラウザ内Providerには別の利用可否判定を設ける。READMEとプライバシー説明には、初回のモデル取得と、翻訳本文の処理場所を記載する。

Argos Translateを採用する場合、既存クライアントの `{ text, source, target }` と `{ translatedText }`、および `/health` に合わせる接続層を用意する。別サービスのURLを指定すればそのまま動くとは想定しない。

### アセットタグの保護

`[icon:名前]` を翻訳対象の通常文字列として無条件に渡さない。衝突しない識別子への退避・復元を試作し、タグの種類と出現数が一致するか検証する。識別子が翻訳で壊れた場合は自動適用せず、確認対象とする。

タグの前後で文章を分割して翻訳すると文脈や語順が崩れるため、その方式を無条件の代替手段にしない。タグが維持されても位置が意味的に適切とは限らないので、アイコンを含む文を個別に品質評価する。

### 数字・用語・既存訳

数字の欠落や変更は、既存の差分表示とつなげて確認できるようにする。用語集は翻訳候補の確認に利用する。エンジンに用語指定機能がない場合、単純な文字列置換で意味や文法を壊さない設計を検証する。

同一原文の再翻訳を避ける。キャッシュを追加する場合は、原文・言語ペア・Provider・取得可能なモデル情報・用語集の変更を考慮する。

### 非同期処理と編集の整合性

翻訳開始時のカード・領域・原文を記録し、処理中に変更された領域へ古い候補を適用しない。キャンセル時は後続処理を止め、既存訳や確認済み候補を壊さない。

### 残る評価の具体的な手順

目的は「実際に使うカードで、規則の意味を保った訳を、手入力より少ない手間で作れるか」を確認すること。以下は今回具体化した初回評価案であり、実施済みの結果や統計的な精度保証ではない。

1. 実際に翻訳したいゲームから、未翻訳の効果文を20領域程度選ぶ。下表の6観点をそれぞれ2例以上含める（1文が複数観点を兼ねてよい）。原文のOCR誤りは先に直しておく。
2. ブラウザ内翻訳で候補を生成し、修正前の候補を保存する。ゲームのルールを理解している人が原文・候補・カード画像を照合する。
3. 各候補を「そのまま使える」「表現・用語だけ修正」「規則の意味を修正」「候補取得失敗」に分類し、修正箇所と確定した訳を記録する。
4. 文字量と下表の観点が近い文を組にし、一方を手入力、他方をブラウザ内翻訳＋修正に割り当てる（各10領域程度）。同じ文を直後に訳し直して記憶で速くなる比較は避ける。両方式とも、原文を読み始めてから内容を確認して適用するまでを計測する。
5. 分類別の件数と両方式の1領域あたりの所要時間の中央値をまとめ、引き続き使う範囲・必ず注意して確認する表現を記録する。別の文の比較なので時間差は目安として扱う。

| 観点 | 具体的に確認すること（例） |
| --- | --- |
| 否定・任意性 | `do not` が禁止のままか。`may` が「してもよい」であり強制になっていないか |
| 条件・順序 | `if` / `unless` の条件が逆転・脱落していないか。`then` の前後の処理順が保たれているか |
| 数量 | `up to 3` が「最大3」であり「必ず3」になっていないか。`each` の各対象への数量やコストが保たれているか |
| 対象 | 自分・相手・全員、手札・山札・捨て札、移動元・移動先が入れ替わっていないか |
| 用語 | 同じゲーム内の `draw` / `discard` / `remove` などを区別し、採用する日本語用語に揃えられるか |
| アイコン位置 | タグの数だけでなく、どの数量・動作に属するかが正しいか。例: 「1 [icon:drop] を消費して2 [icon:sun] を得る」の消費と獲得が逆転していないか |

記録する項目: カード・領域ID、確認観点、原文、修正前の候補、分類、修正理由、確定訳、方式、所要秒数。評価日・Chromeバージョン・使用ゲームも記録する。初回モデル取得時間は通常の翻訳作業時間と分け、候補取得失敗の再試行時間は作業時間に含める。

**この評価の完了条件**は、6観点の実例と分類・修正内容・所要時間が記録され、結果を踏まえた利用方針が決まっていること。誤訳ゼロや特定の時間短縮率を必須条件にはしない。規則の意味を変える誤訳が目立つ場合は該当表現を重点確認対象にし、修正込みで手入力より遅い場合は対象範囲やエンジンを見直す。これは追加評価であり、現在の試験機能の実装完了とは分けて扱う。
