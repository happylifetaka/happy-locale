# 計画: ゲーム別OCR領域検出プロファイルと生成AIによる設定作成

作成日: 2026-09-19

状態: 提案。プロファイル機能・生成AI向け作成支援は未実装。現在の共通処理の条件は[検出・補正条件一覧](../verification/ocr-detection-conditions.md)を参照。利用者提供画像の検証記録は公開リポジトリに含めない。

## 背景と目的

領域候補の検出で、タイトルの一部を囲む小さい候補と、タイトルから効果文までを覆う大きな候補が重なる事例が報告された。一方、正しく検出できるカードもある。汎用の閾値変更だけで既存の成功例を悪化させず、ゲームやカードのレイアウトに応じて検出を調整できるようにする。

今回のゲームには、利用者の説明によると概ね次の要素がある。

- 名前
- 種別
- 装飾付き見出し（なし、または複数の場合もある）
- 効果の文章（複数の場合もある）

これは当該ゲームの構造であり、HappyLocale全体の固定仕様にはしない。ゲーム固有の規則を読み込める「領域検出プロファイル」として分離し、複数画像を生成AIで分析して作れるようにする。

## 現状と原因調査

- [useRegionCandidates.ts](../../app/composables/useRegionCandidates.ts) と [useBatchOCR.ts](../../app/composables/useBatchOCR.ts) は、画像全体を2倍に拡大して `sparse-text` 指定でOCRする。
- [tesseract.ts](../../app/services/ocr/tesseract.ts) は行・単語の座標を返すが、行に元のブロック・段落の識別情報を保持していない。
- [candidates.ts](../../app/services/ocr/candidates.ts) は信頼度等で行を絞り、同一行の断片復元、行間・横方向の重なり・大文字主体のラベル境界を使って結合し、外接矩形を候補にする。OCR自体が返す異常な行矩形や、候補間の包含・重なりを解決する工程は未実装。
- 候補の選択・枠調整・行数の中央での分割は既存機能。確定済み領域の配置を再利用するレイアウトテンプレートもある。

実画像比較で、アプリ側の連鎖的な行結合と、OCR自体が大きな行矩形を返す事例を確認した。共通処理の結合改善は実施済みだが、元の行矩形の異常や読み落としは残る。同一タイトルが別々に認識された場合も、単に大きい枠を削除すると本文が失われるため、包含関係だけで候補を捨てない。

Tesseractの段落境界は判断材料の一つとし、必ず正しい意味上の区切りとは扱わない。特に現在の認識モードで、段落境界を結合禁止条件にすると過分割しないか実測する。

## 採用する構成

初期版は、実行コードを含まないJSON設定と共通の検出エンジンで構成する。アプリに設定を読み込むことで、ゲーム別の拡張として使えるようにする。任意のJavaScript、追加Worker、外部モデルのダウンロードを行うプラグイン機構は対象外とする。

役割は次のように分ける。

| 構成要素 | 役割 |
| --- | --- |
| OCR Provider | 文字・行・単語・認識時の構造を取得する |
| 共通の検出エンジン | 行の再構成、結合・分割、役割推定、候補間の整合性を評価する |
| 領域検出プロファイル | ゲームごとの位置・文字高・間隔・要素の出現規則を指定する |
| 候補確認UI | プレビュー、設定調整、手動修正、確認後の追加を行う |
| AI向け作成支援 | 複数画像からプロファイル案を作るための仕様・指示文・評価手順を提供する |

プロファイルなしの汎用検出を残す。設定だけで未対応の画像解析が実現するわけではなく、検出エンジンが実装した特徴だけを設定可能にする。

## プロファイルに持たせる情報

以下はスキーマ設計案であり、確定済みの読込形式ではない。実画像調査後にJSON Schemaと最小例を定義する。

| 項目 | 内容 |
| --- | --- |
| 識別と互換性 | 形式バージョン、プロファイルID、改訂番号、表示名、説明、必要なエンジン機能 |
| レイアウトの種類 | 同じゲーム内の異なる配置を複数定義。初期版は利用者が選択する |
| 要素の役割 | 任意の役割IDと表示名。名前・種別・見出し・効果文は設定例として扱う |
| 出現規則 | 任意・必須の期待、出現回数の範囲、繰り返し、前後関係 |
| 位置の傾向 | 画像幅・高さに対する0〜1の相対範囲、左右・中央揃えの傾向 |
| 文字と行の特徴 | 相対的な文字高、行間、文字高の比率、結合・分割の許容範囲 |
| 候補フィルタ | 短文・数字・記号を扱う条件、信頼度の下限、余白 |
| 再認識 | 対応済みのOCRレイアウト指定と、限定範囲の再OCR条件・上限 |

位置や出現規則は原則として評価の手掛かりにする。期待する要素が見つからなくても、存在しない文章や空の領域を補完しない。未知の役割や判断できない文字は、未分類の候補として確認できるようにする。

今回のゲームでは「見出し→効果文」の繰り返しと、見出しなしの効果文を表現する。見出しと効果文が常に一対一であるとは仮定しない。必須項目や回数の上限は画像分析後に決める。

装飾の色・形・横線の特徴は後続段階で検討する。初期版の設定には未対応項目を入れず、未知の設定を黙って無視しない。

## 検出処理の方針

1. 画像全体のOCR結果を取得し、元画像座標へ戻す。行・単語と元の構造の対応を保持する。
2. 異常に大きな行矩形、同じ高さで分かれたタイトル断片、文字と装飾の混在を調べる。必要な場合だけ、単語座標による行の再構成や限定範囲の再OCRを行う。
3. 選択したプロファイルの位置・文字高・前後関係から役割候補を求める。
4. 行間、文字高の変化、整列、役割の境界を評価して行をまとめる。結合の連鎖で異なる要素を巻き込まないよう、直前行だけでなくグループ全体も評価する。
5. 候補同士の重複・包含を、元の行・単語の対応に基づいて評価する。外接矩形が重なるだけの候補と、同じ文字を二重に含む候補を区別する。
6. 曖昧な結果は確認対象として表示する。検出できなかった文字を生成AIで補って原文に混ぜない。

OCRの文字認識信頼度と、領域のまとまり・役割の評価は別に扱う。規則の一致スコアを正解確率として表示しない。

## 利用者の操作

1. OCRタブで「汎用」または読み込んだプロファイルを選び、必要ならレイアウトの種類を選ぶ。
2. 領域候補を取得し、枠・原文・役割を確認する。
3. 詳細設定で結合の強さや文字高の許容差等を調整し、再プレビューする。認識済み座標だけで済む変更は再OCRしない。
4. 設定変更が再OCRを必要とする場合は、その旨を表示する。手動調整済み候補の置き換えは明示的な再検出操作で行う。
5. 候補を必要に応じて修正し、選択したものだけ確定する。
6. 調整したプロファイルを別名・別改訂で書き出し、同じゲームで再利用する。

一括OCRにも同じ検出処理を使う。異なるレイアウトが混在する場合は対象カード群ごとに選択できる設計とし、レイアウトの自動選択は評価後に検討する。確定済み領域はプロファイル変更だけでは変更しない。

既存の配置テンプレートは「決まった枠の再配置」、プロファイルは「画像ごとの検出の調整」として共存させる。手動の候補結合・任意行間での分割は、[文章領域の自動選択と微調整](region-selection.md)と共通の実装にする。

## 生成AIによる作成フロー

初期版はHappyLocaleからAIへ直接接続せず、仕様と指示文を用意し、利用者が選んだAI環境で分析してJSONを作る方式とする。

1. 成功例・失敗例、短文・長文、見出しの有無・繰り返し、異なる配置を含む代表画像を選ぶ。分析用と評価用を分け、評価用は生成時に渡さない。
2. JSON Schema、対応する特徴一覧、最小設定例と、分析手順の指示文をAIに渡す。必要なら利用者の明示操作でOCR座標も書き出せるようにする。
3. AIは画像ごとの要素と例外、共通する配置、複数レイアウトの必要性を分析する。架空の設定キーや未対応の検出方式を出力しないよう指示する。
4. AIからプロファイルJSONと、根拠・不確実な点を記した別の分析メモを受け取る。生成時に全カード共通と断定しない。
5. HappyLocaleで形式と機能対応を検証して読み込み、生成に使っていないカードで試す。
6. 誤結合・過分割・見落としを確認して修正し、採用する改訂を保存する。

画像は利用者が選択した作成時だけAIへ提供する。外部AIを使う場合はそのサービスへ画像が渡ることを説明し、アプリからの暗黙送信は追加しない。日常のOCRとプロファイル適用は端末内で完結する。

AIへの直接接続、複数案の自動探索、結果からの自動学習は後続の別計画とする。公開版の外部Translation Endpoint禁止を転用・解除して実装しない。

## 保存・責務・入力検証

- 新しいスキーマ・解析・検出処理は `app/services/ocr/` を中心に分離し、候補UIとcomposableから利用する。`CardEditor.vue`に解析処理を集中させない。
- プロジェクトには採用した設定のスナップショットと改訂、選択したレイアウトをJSON互換で保存する方針とする。外部ファイルへの参照だけに依存させない。
- 保存形式を変更する段階でバージョン方針を確定し、旧形式の読込・移行、未知バージョン拒否、保存失敗時の整合性・バックアップをテストする。
- 単体のプロファイルJSONを読み書きできるようにし、同一IDの別改訂は無言で上書きしない。画像・フォント・実行コード・認証情報は同梱しない。
- 読込時は未知バージョン・未対応設定・不正な数値・範囲・重複IDを拒否し、ファイルサイズ、規則数、再OCR回数に上限を設ける。外部URL取得や設定内コードの評価をしない。
- OCR実行中のカード・画像・プロファイル改訂・設定変更を照合し、古い結果を反映しない。キャンセル・画面破棄後も同様に扱う。
- 設定変更の未保存判定、候補編集の取消、確定時のUndo/Redo、一括OCRへの反映を既存の操作経路に統合する。

- [x] 利用者が指定した画像一覧から、成功例と問題例を含む代表画像を確認する（全37枚の一覧・実OCR・候補枠を確認）。
- [ ] 問題画像のOCR行・単語・結合前後の矩形をローカルで比較し、巨大候補と内包候補の発生箇所を特定する（巨大結合は再現・改善。添付画面と同じ内包候補の完全一致再現は未完了）。
- [ ] 人が期待する領域・役割を記録し、分析用と評価用を分ける。
- [ ] 現行方式の誤結合、過分割、見落とし、手動修正回数、処理時間を記録する。

利用者の画像やOCR全文を公開リポジトリ・公開テスト素材に追加しない。公開テストは合成画像・架空の文章と座標で再現し、実画像の検証はローカルで行う。

## 検証と採用判断

単体テストは、同一行の断片、巨大なOCR行、通常の複数行本文、見出しと本文の境界、中央揃え、アイコン入り文章、短い見出し、候補の重複・包含を中心に行う。設定の異常系と保存形式の互換性も検証する。

UI・結合テストでは、読込失敗時の状態保持、プロファイル切替、手動編集後の再検出、個別・一括OCRの一致、取消・Undo/Redo、カード切替・設定変更中の遅延結果破棄を確認する。E2Eのモック結果と、Chrome上の実Tesseractによる実画像確認は区別して報告する。

評価は候補件数の一致だけで判断しない。期待領域に対する見落とし・余分な候補・誤結合・過分割、枠の位置と文字の欠落、役割の一致、手動修正回数・確定時間、処理時間・再OCR回数を記録する。文字認識の誤りと領域分割の誤りは別々に集計する。

数値の採用基準は段階0の測定後、設定調整を始める前に定める。既存の成功例の悪化と失敗例の改善を両方報告し、平均値だけで重大な見落としを隠さない。未使用画像でも修正作業量が減り、本文の欠落・重複が増えないことを採用の条件とする。
